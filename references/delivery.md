# 导出与验收

## 进入导出阶段

先按 planning.md 判断是否已进入详细规划：核心方向和会改变路线的关键安排已由用户表达、选定或明确交由你决定，或用户明确要求导出当前草案/已有计划。只有出发地、日期、人数和预算时，不能因为模板可以填写就自动生成 HTML。交付条件性草案用于表达未落实的外部条件或用户要求的假设方案，不能替代对核心偏好的了解。

## 命令

Python 3 标准库即可。从任意目录调用 Skill 的 scripts/travel_plan.py；输入输出路径显式给出。`init` 创建完整字段骨架；也可参考 assets/demo-plan.json（所有地名、规则和订单都是模拟，不可用于出行）。

```text
python <skill>/scripts/travel_plan.py check plan.json --as-of YYYY-MM-DD
python <skill>/scripts/travel_plan.py render plan.json --out travel-plan.html --as-of YYYY-MM-DD
python <skill>/scripts/travel_plan.py audit travel-plan.html
```

CLI 的 stdout/stderr 统一使用 UTF-8。check 输出 JSON：schema_errors、blockers、warnings、effective_status、budget。退出码 2 表示结构错误，1 表示可行性阻断，0 表示已实现的检查未发现阻断。render 遇结构错误不写文件；可行性阻断会写醒目“条件性方案”及问题清单并返回 1，不能因生成文件就说可出发。输出已有文件时默认拒绝，另用新文件名；显式 `--force` 才覆盖。

audit 检查静态资源/API/CSS 依赖和本地资源引用（只允许自包含资源与显式在线链接），不证明浏览器兼容。链接联网属于增强能力，不算核心依赖。未知模板改动后不能仅凭 audit 通过就交付。

## 内容验收

默认导出旅行手帐版式：奶油色纸张、陶土橙标签、行程时间线与可勾选清单。封面为杂志刊头式纯排版：细线夹一行刊头小字（日期 · 人数 · 预计必需花费），大标题与出发地→目的地，底部细线后分三栏大数字（行程天数 / 预计必需花费 / 出发清单进度）。日程在清单前，偏好与勾选说明可折叠；重要阻断项和订单状态保持直接可见。来源引用以上标编号指向"随身资料夹"，查证记录默认折叠分层展示，来源冲突保持直接可见。不使用装饰插画；不依赖在线字体、图片或其他资源。全程同一 UTC 偏移的行程（如国内游）省略 UTC 标注；出现多个偏移（跨时区）时短时刻旁保留日期及 UTC 偏移，跨午夜时展示两端完整日期和偏移，避免只看时钟误读。

人工复核来源、地址真实性、时间窗口含义、行李、首尾天、用餐/休息、强度、已知订单和风险备选。脚本只检查显式输入条件，不推断未记录的营业日或隐含需求。constraints.status 的 satisfied 必须有 evidence；语义正确性仍由规划者负责。

参考 budget 范围要与用户硬约束一致。所有关键 unresolved、booking、source 冲突应可见；探索方案允许未知，不能伪装 ready。

## 浏览器离线测试

### 待办勾选

HTML 的待办支持点击标题、复选框或键盘空格切换，初始值来自 tasks.status。勾选进度仅保存在当前浏览器的 localStorage，不回写 plan.json，也不改变订单确认记录和生成时的核验结论。内容版本由 plan.json 除 generated_at 外的全部内容生成指纹，再按待办 ID 分别保存；仅重新导出或改变生成时间不重置进度，内容或 revision 改变则采用新版初始值。

保存成功时说明保存范围；浏览器拒绝读写时降级为当前页面内勾选并提示无法保存。禁用脚本时复选框不可操作，仍展示生成时状态和全部事项。换浏览器、换设备、清理浏览器数据或改变本地文件打开方式后可能无法恢复，不承诺跨设备同步。

验证初始 pending/done、标题点击、键盘切换、勾选与取消后的重载恢复、不同内容版本隔离；模拟存储读取和写入拒绝，确认页面可继续勾选且显示降级提示。检查顶部核验结论、订单摘要不随勾选改变。

优先用环境已有且授权的浏览器自动化工具。当前端工具不可用时只报告静态检查，不声称做过动态离线检查。

1. 用 `file://` 打开生成文件。在独立的测试页面/上下文阻断网络请求或设为 offline，再重新加载，记录实际方法。不要改变用户日常浏览器全局网络设置。
2. 查看手机尺寸（例如 390×844、窄屏 320px）有无横向溢出、文字遮挡，检查不同日期的跳转、问题清单、预算及来源完整显示。
3. 点击复制；API 拒绝时应显示“长按或选择地址复制”，地址仍可选中，不能误报已复制。
4. 在禁用脚本的独立测试上下文重开文件，确认全部日期、地址、预约和预算可读。无法禁用时明确此项未实测；模板按静态 HTML 生成，不能靠 JS 注入核心内容。
5. 检查浏览器控制台错误和网络尝试，保留简短结果及必要截图。真实手机保存/打开流程未测试则单独标记，不以桌面模拟冒充。

## 打开与分享

告诉用户保存 HTML 后用支持本地网页的浏览器/查看器打开；聊天应用预览器的脚本支持不可假定。首次使用请在实际手机离线打开确认。若目标设备无法顺利打开，按已有工具能力导出静态 PDF，不能仅改扩展名；PDF 也需要检查。模板自带打印排版，浏览器可另存 PDF。

分享版只保留必要集合、路线、餐饮和注意事项；导出前删掉不必要的订单身份和联系方式。默认脚本不自动生成分享版或发布链接。

### 搭子卡：推荐内容 → 审核文字 → 自由设计

先利用已有的分享对象、旅行内容和用途，推荐一份简短内容组合，并列出可增减项。例如“建议写日期、这次想做的两三件事和还没定的住宿；集合、费用也可以加”。用户选择后起草，不逐个栏目盘问；用户已给出内容时直接起草。允许“我们商量好的安排”等自由标题，不默认套情侣文案、群聊称呼、接龙、投票或 AA。预设栏目是灵感，不是必须填的表单。

将完整文案保存为 `card.draft`，在对话中展示供用户增删修改。图片中的标题、装饰性文字也算文案，不在设计时偷偷添加口号。审核稿不是附赠的群聊文字成品。不固定显示人数、天数、费用或核验状态块；详细核验清单留在攻略，只将影响卡上约定的未定事项自然地写进稿件，例如“酒店还没定，我们再一起挑”，不把未知写成已确认。对模拟内容保留明显的虚构标注。

需要保存审核稿时运行默认命令；可以直接在对话中审阅，无需用户打开文件：

```text
python <skill>/scripts/travel_plan.py card plan.json -o dazi-card
```

默认只生成 `card-draft.txt`，不会启动浏览器。用户确认当前文案后，AI 按内容设计自包含 HTML/CSS，用户风格要求或参考图优先。无需让用户每次选择模板；允许自由安排标题、段落、图形、配色和字体，默认使用本地字体、CSS 和内嵌 SVG，不添加图片生成服务或联网素材依赖。不能只替换原模板的颜色就宣称独立设计。可参考 `assets/card-examples/` 的两种示例，但不要把它们变成新的强制模板。

#### 设计文件约定

- UTF-8 完整静态 HTML，带 head/body 和正确闭合的标签；无外部资源、脚本或事件属性。核心文案直接在 HTML 中，不放进 CSS 伪元素、图片、Canvas 或隐藏模板。分页控制由导出器注入。
- 每页一个 `.sheet`，按 DOM 顺序标为 `id="page-1"`、`page-2` 等，不嵌套。导出器只固定每页 1080×1440、零外边距和分页显示；设计自定内边距、字体、布局与配色，不加入动画。
- `.sheet` 中正文的 DOM 阅读顺序与 `card.draft` 一致，可跨标签分行。脚本忽略空白差异后逐字比对；增加、删除或更改文字都会拒绝出图。调整视觉位置不必更改阅读顺序。
- 每页一处 `<footer data-card-credit>由 travel-planner 生成 · @杰纶hhh</footer>`，可自定义位置和轻量样式；作者取 `card.author`，缺省为“杰纶hhh”。署名不计入文案比对，且必须与作者完全一致，不能夹带其他文本。正文与署名之外不加可见文字。
- 不使用省略号、单行裁切或隐藏超出的文案来塞入画布。优先调整留白、宽度、字号与换行，并确保手机查看仍可读；确实装不下再提出精简稿，重新审核。只有用户同意才增加图片。

确认文案后按需执行：

```text
python <skill>/scripts/travel_plan.py card plan.json -o dazi-card --format image --approved --html design.html
python <skill>/scripts/travel_plan.py card plan.json -o dazi-card --format text --approved
```

图片命令只生成 PNG 和内部 `dazi-card.html`；文字命令只导出原稿 `dazi-card.txt`。两者都需要时才分别执行。“做张卡”默认图片；只表达“发群里”等分享用途而未说明形式时，一次确认所需形式。“只要文字”也先审稿，不继续出图。图片与文字复用同一已确认文案时不重审；为某种形式改写内容时展示修改稿再确认。只修改配色、字体、布局不重审文字。

`--approved` 由 Agent 在用户实际确认当前文案后使用，旧行程的确认不能代替卡片审核。实质改变稿件须重新确认。新流程的自由稿缺少 `--html` 会拒绝出图，不退回固定模板。无自由稿的旧 `card.sections` 仍走原模板；不为新卡片刻意删掉 `draft` 来绕回旧流程。多张需明确同意并追加 `--allow-multiple`。默认拒绝覆盖，另用新目录；明确覆盖时才加 `--force`。

#### 验收与交付

退出码沿用 `check`：2 为格式/运行错误，1 为行程仍有可行性阻断，0 为机械检查没有阻断。自由稿不自动抄写 blockers，但返回报告保留原核验结果；图片成功不表示行程就绪。`card.stage` 区分 draft/image/text。只有 image 阶段 `images` 非空且与 `expected_images` 一致才表示出图完成。若 `image_error` 存在，用当前可用浏览器工具打开生成 HTML 并截图；无浏览器能力时如实报告未完成，不能交付 HTML 冒充图片。

在浏览器中阻断网络并重新打开，检查没有外部请求、脚本错误、裁切或遮挡。逐字对照审核稿，检查 DOM 文字实际可见、字号可读、署名不过分抢眼、页数符合要求。静态文字匹配不能证明可见，也不能证明事实正确。出图前后均核对与原行程相关的事实；图片不依赖额外文字文件。仅改卡片时不必重跑手帐全部交互测试。

`assets/card-examples/copy.json` 保存双人和朋友两份虚构自由稿，配套 HTML 在同目录；它们是可复用的设计示例及测试素材。README 的预览应对应实际生成结果。微信粘贴和真实手机查看只有实际测试后才能称为已验证。卡片和文字均不自动发送。

不要为基础交付引入 PWA、Service Worker、账号或后台。它们只有在用户确有需求且验证环境支持时才属于新增范围。
